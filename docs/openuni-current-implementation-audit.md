# OpenUni 当前实现完成度审计

审计时间：2026-04-24  
审计对象：当前仓库实现 vs 原始产品说明文档《OpenUni》

## 1. 总体判断

当前 OpenUni 已经不是“静态比赛稿”，而是一个完成度较高的高保真竞赛原型 / 单校 MVP。  
核心主链路已经形成：

- 发现：北航来源池 + 发现页 + 来源关注 / 同步
- 判断：信号页 + 信号详情页 + Ask 决策支持
- 行动：提醒页 + 设置报名提醒 + 成功页
- 个性化依据：我的阶段 + 学院规则 PDF 导入 + 规则事实提取

如果按竞赛原型完成度判断，当前大致处于 `75% - 85%` 区间，已经具备比较完整的“产品故事 + 可演示路径 + AI 能力落地”。  
当前更适合做“收口和比赛表达强化”，不适合再继续横向扩功能。

我对当前实现的总体判断是：

- 核心产品定位基本成立：它仍然是“AI campus key-signal assistant”，不是泛校园资讯平台。
- 最强的完成区已经形成：`信号页 / 详情页 / Ask / 规则导入 / 核心场景闭环`。
- 最近补上的“发现层”已经有价值，但还偏 MVP，和竞赛级成品之间仍有一层“表达与稳定性”的差距。
- 当前最大的风险不是“功能不够多”，而是“功能已经够多，需要更明确收口，避免显得过宽”。

## 2. 按说明文档逐项对照

### 2.1 用户洞察与问题定义

- 状态：`已完成`
- 当前已有：onboarding、信号页文案、详情页推荐逻辑、Ask 上下文都明确围绕“大一、信息弱连接、不会主动刷很多群、希望知道什么值得做”的用户画像构建；首页和详情页都在强调“高收益、低可见、强时效”而不是泛内容浏览。
- 仍缺什么：当前实现主要服务于一个核心画像，尚未展示“多类用户画像切换后的明显差异”，所以“用户洞察”更多是被单一场景验证，而不是被多场景验证。
- 审计判断：说明文档中的核心问题定义已经被产品界面和主流程很好地承接，且没有被后续功能扩张冲掉。

### 2.2 使用场景

- 状态：`部分完成`
- 当前已有：文档中的主场景“女生游泳比赛其实与综测/体育项相关，是高价值、低可见、强时效机会”已经被完整实现为可演示闭环；创新项目、奖学金说明会、英语竞赛、科研训练营等作为相关信号或发现候选也已存在。
- 仍缺什么：真正完整打通的仍然只有一个主场景 `/signal/swim`。其他机会大多存在于信号卡、候选卡、Related signals 或数据层中，但还没有独立的详情页 / 判断页 / Ask 路径。
- 审计判断：核心场景完成度高，但“场景覆盖面”仍主要停留在“一个 fully-built 场景 + 多个 seeded 陪衬场景”。

### 2.3 产品概述

- 状态：`已实现但与文档不完全一致`
- 当前已有：当前产品已经具备“发现层 + 信号层 + 行动层 + 个性化依据层”，整体比最初比赛 demo 更像一个单校 MVP。
- 与文档不完全一致的地方：原文档更像“小而精的核心 demo”，而当前实现已经扩展到“北航发现层 + 来源池 + 规则导入 + 规则知识层 + 自然语言关注来源”。这让产品更真实，但也让范围略大于原始竞赛稿的最小叙事。
- 审计判断：定位仍然对，但产品已经从“核心 demo”向“单校 MVP”外扩，需要在比赛表达里主动强调“这是北航单校 MVP，而不是大而全平台”。

### 2.4 核心功能

- 状态：`部分完成`
- 当前已有：
- 个性化 onboarding 已完成。
- 信号页已完成，且具备“与我强相关 / 高收益机会 / 即将截止 / 当前阶段推荐”的组织逻辑。
- 信号详情页已完成，且更像“决策页”而不是“阅读页”。
- Ask 已完成真实服务端模型调用，并支持决策型 / 事实型 / 探索比较型问题。
- 提醒页与成功页已完成基础行动闭环。
- 我的阶段页已完成，并且接入了学院规则导入。
- 发现页已具备来源池、候选、已进入信号流、来源状态。
- 仍缺什么：
- 多信号详情页尚未铺开。
- 提醒仍然是 demo 级状态管理，不是真实提醒系统。
- “行动”仍停留在提醒 / 查看路径 / 收藏式表达，没有继续下探到更具体的任务编排。
- 审计判断：功能 breadth 已经足够比赛使用，但 functional depth 主要集中在一个主信号上。

### 2.5 产品架构 / 功能图

- 状态：`部分完成`
- 当前已有：当前代码已经明显映射出文档中的几层结构：来源 / 发现层、信号识别层、用户画像层、判断解释层、提醒行动层；`data/openuni-demo-kb.ts`、`data/buaa-discovery-kb.ts`、`app/api/ask/route.ts`、`app/api/rule/route.ts`、`app/api/discovery/route.ts` 共同构成了一个简化但清晰的 AI-native 产品架构。
- 仍缺什么：真正的“持续采集 / 调度 / 生产级存储 / 多来源连接器 / 多学校扩展”并未实现，当前是本地化、受控、demo-first 的架构。
- 审计判断：架构表达已经足够支撑比赛叙事，但还不是完整工程系统；作为竞赛作品这是合理的。

### 2.6 交互流程

- 状态：`已完成`
- 当前已有：`onboarding -> 信号页 -> 信号详情 -> Ask -> 成功页 / 提醒页` 这条链路完整；另外已经补出 `发现 -> 信号` 的前链路，以及 `我的阶段 -> 规则导入 -> 返回判断依据` 的后链路。
- 当前表现好的地方：Ask 页已支持回到信号页 / 首页；信号详情与成功页的 CTA 关系清楚；底部导航已把“发现 / 信号 / 提醒 / 我的阶段”收进一个统一壳层。
- 仍缺什么：跨多信号的二次跳转仍偏少；提醒页和成功页之间更多是状态展示，不是完整 action management。
- 审计判断：对比赛 demo 来说，交互闭环已经成立，而且比原始要求更完整。

### 2.7 创新与差异化

- 状态：`部分完成`
- 当前已有：
- “不是校园信息流，而是 key-signal 判断助手”的差异化已经比较清楚。
- Ask 已经不是聊天框，而是结构化判断层。
- 导入学院规则 PDF -> 解析规则事实 -> 接入首页 / 详情 / Ask，这一点有明显差异化。
- 发现页的“来源池 -> 候选 -> 进入信号流”也体现了产品的 AI-native 识别逻辑。
- 仍缺什么：这些创新点目前更多是“做出来了”，但还没有被产品自己总结得足够清楚。用户第一次进入时，仍需要稍微理解一下才能意识到这些能力的独特性。
- 审计判断：创新已经存在，但“创新表达层”还不够锋利。

### 2.8 AI 核心能力

- 状态：`已完成`
- 当前已有：
- Ask 使用真实 DeepSeek 服务端调用。
- Ask 支持题型分类、结构化回答、事实型证据展示、越界问题约束、fallback。
- 规则导入支持 PDF 文本提取、规则事实结构化抽取、字段级 evidence。
- 发现页支持模型辅助页面读取与 discovery candidate 提取。
- 当前不是单纯“把 LLM 放在聊天页里”，而是多个 AI 节点嵌入产品流程。
- 仍缺什么：还没有真正做出“跨多个来源、持续演进的模型反馈闭环”；当前更像多节点 AI 工作流 MVP。
- 审计判断：对于竞赛原型来说，这部分已经是强项。

### 2.9 AI 如何解决痛点

- 状态：`已完成`
- 当前已有：
- 发现页解决“我不知道北航最近发生了什么”。
- 信号页解决“哪些内容对我当前阶段最重要”。
- 详情页解决“为什么值得判断 / 值不值得做”。
- Ask 解决“我还想进一步判断、比较、追问事实”。
- 规则导入解决“不同学院规则不同，不能只靠通用样例”。
- 仍缺什么：当前产品对“持续长期陪伴”的表达还不算强，更偏当前周期的机会识别。
- 审计判断：AI 不是噱头，而是已经实际进入痛点解法。

### 2.10 AI 技术方案

- 状态：`部分完成`
- 当前已有：
- 规则层：PDF -> 文本提取 -> 章节/表格识别 -> fallback facts + model merge -> 存储。
- Ask 层：profile + signal + sources + active rule -> server API -> typed answer / fallback。
- 发现层：source watchlist -> page fetch -> model-assisted extraction -> candidate generation -> source effectiveness update。
- 仍缺什么：
- 当前仍是本地持久化与受控同步，不是生产级可靠管线。
- 对外网页抓取在网络、可访问性、页面结构变化方面的鲁棒性还比较弱。
- 没有真正的定时调度或异步队列。
- 审计判断：技术路线已经能讲清楚，但工程化程度仍是 MVP。

### 2.11 落地可行性

- 状态：`部分完成`
- 当前已有：
- 本地 demo 能真实跑通主要链路。
- Ask、规则导入、发现同步都已经不是纯静态假动作。
- 产品结构已经可以向“北航单校 MVP”解释。
- 仍缺什么：
- 当前的规则存储和 discovery runtime store 更适合本地或长驻服务，不太适合直接无改造地上纯 serverless。
- 来源同步的稳定性仍受外部页面可访问性影响。
- 多学院 / 多学校扩展仍需进一步抽象。
- 审计判断：可行性已被证明，但更偏“原型可行”，不是“业务已 ready”。

### 2.12 商业化思考

- 状态：`未完成`
- 当前已有：产品里有一些能够指向商业化的影子，例如单校规则层、来源池、持续关注、提醒服务、QQ/PCG 生态承载感。
- 仍缺什么：当前实现没有把商业化路径显性化，也没有在产品中体现 B 端 / 校方 / 平台侧价值分层。
- 审计判断：这部分仍停留在说明文档层，不在产品当前实现里。

## 3. 当前已形成的产品亮点

- `Ask 已经像真正的决策支持层`：不是通用聊天，而是围绕当前信号、用户画像、规则事实做结构化判断。
- `学院规则 PDF 功能已经真正接入主流程`：不是独立 demo，而是接到了首页、详情页和 Ask。
- `发现页和信号页已经形成分工`：发现更广，信号更窄，这一点已经比很多同类竞赛稿更完整。
- `产品已经具备单校 MVP 质感`：北航发现层、来源池、规则导入、持续关注来源，让它不再像纯概念稿。
- `行动闭环基本成立`：设置提醒、查看报名路径、提醒页状态、成功页，都能支撑 demo 录制。

## 4. 当前最明显的完成度短板

- `多场景深度不足`：真正 fully-built 的只有 swim 主场景，其他信号更多是陪衬。
- `发现层还偏 MVP`：逻辑已成立，但内容质量、同步结果表达、来源命中解释还不够“像成熟产品”。
- `产品表达略有外扩风险`：当前已经从“小而精 demo”扩到“单校 MVP”，再加功能容易变得大而散。
- `QQ / PCG 生态感已出现但还不够强`：壳层、命名和服务感有了，但还没有强到让评委一眼感到“这很适合挂在 QQ 校园助手里”。
- `商业化与平台价值没有进入产品表现层`：如果比赛看重商业化，这会是一个空档。

## 5. 最值得优先打磨的 3-5 个点

- `第一优先：收口产品叙事，而不是再扩功能`
  当前最该做的是把“发现 -> 信号 -> Ask -> 提醒 -> 我的阶段 / 规则依据”这套故事讲得更清楚，让每一页首屏都更明确承担自己的角色。

- `第二优先：再打磨发现页的“有用感”`
  发现页现在已经比之前好很多，但还可以继续强化“北航最近发生了什么”与“哪些值得我继续看”的信息密度平衡，尤其是同步结果后的反馈感。

- `第三优先：让规则导入的价值更可见`
  规则导入其实已经很强，但需要更直观地让用户感受到“导入前后判断依据变了”“这是单校定制，不是样例规则”。

- `第四优先：再强化 QQ / PCG ecosystem packaging`
  不是加大 logo，而是让“QQ 校园助手 / OpenUni / AI 信号识别 + 提醒服务”这套包装更统一、更自然。

- `第五优先：补强第二条完整场景`
  如果还有时间，最值的不是再加很多模块，而是把第二条信号做成接近 swim 的完整度，这会显著提高“不是单点 demo”的可信度。

## 6. 建议：下一轮应该是“收口”还是“补功能”

建议明确转入：`收口为主，少量补强，不再横向扩功能`。

理由如下：

- 当前功能面已经足以支撑比赛讲述。
- 继续加功能，会进一步稀释“小而精”的产品印象。
- 当前最需要的是让已有能力之间的关系更清楚，而不是让能力种类更多。
- 对比赛来说，“清晰、有判断力、有收口感”的产品，通常比“模块更多”的产品更占优势。

更具体地说：

- 应该继续做：表达统一、首屏节奏、功能之间的桥接、第二场景补强、规则价值显性化、发现页同步结果可视化。
- 不建议继续做：更多 tab、更多后台、更多管理页、更多来源运营逻辑、更多泛校园内容功能。

## 7. 对几个关键问题的直接结论

- `现在还算“小而精”吗？`
  基本还算，但已经站在边界上了。再扩两轮功能就容易变成“大而全的演示拼盘”。

- `发现页和信号页现在区分清楚吗？`
  已经清楚很多，方向是对的；但发现页仍然需要在“更宏观、更轻扫读”上继续收口一轮。

- `学院规则 PDF 功能是否真正接进产品？`
  是，而且是当前实现里最有竞争力的差异化点之一。

- `Ask 是否已经像真实决策支持层？`
  是。它已经超出“比赛 demo 聊天框”的水平。

- `发现 -> 判断 -> 行动 闭环是否成立？`
  核心场景上成立，且可以演示；如果追求产品完整度，还差“第二场景也成立”。

- `QQ / PCG 方向是否足够可见？`
  可见，但还不够强。当前是“有这个方向”，还没到“这是天然属于这个生态”的程度。

- `哪些部分已经 demo-ready？`
  信号页、详情页、Ask、规则导入、主场景闭环、提醒成功页。

- `哪些部分还偏 rough？`
  发现页同步体验、用户自定义来源的价值显化、第二完整场景、商业化表达。
